# Database design

PostgreSQL (Supabase). Five ordered migrations in `supabase/migrations`:

| File | Contents |
|---|---|
| `..01_core.sql` | helper functions, all tables, constraints, indexes |
| `..02_logic.sql` | triggers: defaults, money rules, balances, bookkeeping, audit |
| `..03_api.sql` | views and RPCs the app calls, dashboards, maintenance helpers |
| `..04_security.sql` | grants and row level security |
| `..05_seed.sql` | starting areas, packages, WhatsApp template, cash/bank accounts |

## Tables

```
auth.users 1-1 profiles 1-0..1 employees >- areas
                                  |
packages -< customers >- areas    +- seller of customers
              |
              +-< monthly_fees (unique per customer + month)
              |        |
              |        +-< payments (composite FK: fee AND customer must match)
              |                 +-< journal_entries   (income / reversal)
              |                 +-< account_transactions >- accounts
              |                 +-< sms_logs
              +-< complaints
sms_templates      company_logs (audit trail)
```

## Rules the database enforces (so the app cannot get them wrong)

**Defaults / auto-fill**
- `customers.customer_code` -> `CUS-00001...` (never reuses an existing code)
- `customers.balance` -> maintained by triggers; `opening_balance` may be negative (advance)
- new / re-activated active customer -> this month's fee is created immediately
- `monthly_fees`: any date in the month is normalised to the 1st; `due_date` = 10th;
  `amount_due` = package fee (snapshot, later package changes do not alter it)
- `payments`: `customer_id` taken from the fee, `receipt_number` = `RCP-YYYY-NNNNNN`,
  `received_by` = logged-in user, method defaults to cash
- `created_by` on complaints / journal / account transactions is stamped from the login
  (it cannot be spoofed and the app does not have to send it)
- `complaints.resolved_at` follows `status`

**Money rules (apply to the app *and* to direct SQL)**
- a payment must be > 0, cannot exceed the fee's remaining amount, and cannot point at
  another customer's fee (composite foreign key + trigger)
- every payment automatically posts a journal income entry and a cash/bank account credit;
  a reversal posts the opposite entries
- payments, fees, journal, account transactions and the audit log can never be deleted
- balances are always recomputed from fees and payments, so they cannot drift

**Leniency (the old schema rejected these)**
- phone: Pakistani mobiles are normalised to `03XXXXXXXXX`; any other 7-15 digit number is kept
- ids are `generated by default`, so imports / restores with explicit ids work
- no extensions needed (no citext / pg_trgm / pgcrypto)
- the audit trigger can never make a real insert fail (problems become warnings)

**Security (RLS)**
- admin: everything except deleting financial records
- staff: customers, own payments, complaints they created / are assigned
  (cannot change balance, package, area, status; hidden fields are ignored on insert)
- anon: only `health_check()`
- money tables have no browser write access; they change through triggers and RPCs

## Maintenance helpers
- `fix_sequences()` - after importing rows with their own ids
- `recompute_all_balances()` - rebuild every customer balance
- `set_config('app.bulk_load','on',true)` inside a transaction - load historical data without side effects
